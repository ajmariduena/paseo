Prompt annotation persistence and handoff history validation
Date: 2026-10-09
Baseline: 78d8fbf0a (plan-machine-handoff-macbook-vps)
Platform: Linux; real temporary files, isolated daemon homes and WebSocket clients.

Regressions
- With the annotation directory blocked by a regular file, two concurrent requests for the same
  message returned rejected/fulfilled. The duplicate incorrectly treated a cache entry as a
  successful write. Both now reject; after repairing storage, retry persists exactly one entry.
- An ordinary permissive read cached damaged metadata as empty, allowing the next prompt to
  overwrite it. New writes now refuse the damaged file and can retry after repair without losing
  earlier entries.
- Handoff projection accepted structurally damaged annotation metadata or reused a stale cached
  copy. Fresh and previously loaded stores now refuse it instead of losing message presentation.
- After both daemons restarted, source release accepted a valid but changed notification record
  even though destination staging held the earlier presentation. Release now returns source_changed
  and keeps the source ready/fenced until the original metadata is restored or the transfer cancelled.

Evidence
- Ten annotation-store cases cover ordinary replay, failed duplicate writes/retry, per-agent
  ordering, capture after queued writes, deletion followed by a new prompt, missing committed files,
  duplicate IDs, malformed hashes, entry count, byte limits, repair retry and preservation of
  damaged files when ordinary replay tolerated their missing presentation.
- Six focused manager cases cover strict handoff reads and the existing notification/sender presentation
  across daemon-style reconstruction. They use the existing in-process test provider, no external API.
- Two network cases cover native and context choices with synthetic Claude transcripts and the
  existing version-only executable. Invalid metadata blocks preparation with the source fenced;
  repair permits staging. After both hosts restart, changed presentation blocks release. Restoring
  the original permits activation and destination history exposes the original notification.
- Final typecheck, lint and formatting output follows. Only the affected suites/cases were run;
  no full local suite, main-daemon restart, provider authentication or external message delivery.

Limits
- The network conversations start closed. These cases prove persistence/reconstruction and
  transaction behavior, not real provider shutdown or continuation, UI rendering or physical hosts.
- This does not add a universal error barrier for background session events or optional durable
  timeline stores. Their failure propagation and recovery remain in the acceptance plan, as do
  launch-time process/configuration ownership and source retirement.
- An atomic annotation write is not a new power-loss durability guarantee for ordinary message
  dispatch. The handoff copies validated presentation into its existing durable archive before ready.
- Existing retention keeps the latest 500 annotation entries; this does not recover already-pruned
  provenance. Source metadata is rechecked before release; later external source edits do not sync.
- Complete handoff remains unadvertised, PR #30 is a draft, and MacBook/VPS and platform gates remain.
