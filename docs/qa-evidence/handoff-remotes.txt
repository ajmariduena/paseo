Git remotes during workspace handoff
Date: 2026-10-09
Baseline: 243b49962 (plan-machine-handoff-macbook-vps)
Platform: Linux; real Git, temporary files, isolated daemon homes and WebSocket clients.

Behavior proved
- The baseline lost origin when reconstructing a checkout; the first regression failed with
  "No such remote 'origin'".
- Effective fetch/push destinations survive capture and restoration, including source insteadOf
  and pushInsteadOf rewrites, multiple fetch URLs, distinct SSH push destinations and implicit
  push following a later fetch-URL change. SSH login names, ports and the exact path remain
  intact; a regression first reproduced dot segments being normalized during password removal.
- HTTP userinfo and passwords are absent from the manifest and installed Git configuration.
  Synthetic credential helpers, SSH commands and source rewrites are not copied or invoked.
- Worktrees and unborn branches retain remote URLs. Restored origin resolves to the expected
  forge identity using the existing resolver, without querying that forge.
- Sanitized destination changes invalidate review or source release; rotating embedded
  credentials alone does not invalidate review. Installed-URL verification permits a different
  global authentication rewrite on the destination.
- Local/file/helper/query/fragment/control-character URLs fail read-only preflight. Incoming
  credentials/helpers, colliding or nonportable names and oversized URL lists fail before the
  destination checkout is created. Error text does not expose the synthetic secret markers.
- A real two-daemon transfer preserves sanitized origin in staging, refuses source release
  after an origin change, and activates after destination restart once the source matches again.

Execution notes
- The workspace file passed all 88 cases before the additional name/limit and SSH path cases.
  The final focused remote run passed all 22 remote cases (71 unrelated cases skipped; 93 total
  in the file). The full local suite was not run.
- The first network attempt read the wrong cwd because the public destination snapshot does
  not expose stagingCwd. The test now reads the private staging path from the isolated daemon.
  The corrected network case passed. The mistaken operation was a read-only git remote get-url;
  it made no repository change. The final network run follows the SSH path correction.
- The helper-signature cleanup initially exposed a TypeScript narrowing error in the URL
  rejection branch. Returning the never-returning rejection explicitly fixed it; final typecheck
  and all 22 remote cases pass. Typecheck/lint and formatting output follows. No browser UI, provider turn, external fetch/push
  or authenticated forge operation was exercised in this slice. No main daemon was restarted.

Limits
- Branch upstreams, custom refspecs, remote-tracking refs and push policies are not reconstructed.
  Source SSH alias definitions and credentials are not transferred. Their availability on the
  destination and authenticated forge behavior need separate evidence/dispositions.
- Physical MacBook/VPS, native/mobile, Electron and version-drift gates remain open. Windows
  ownership release/activation remains unavailable pending directory durability.
- Complete handoff remains unadvertised and PR #30 remains a draft. This closes remote-URL
  transport coverage, not the complete acceptance plan.
